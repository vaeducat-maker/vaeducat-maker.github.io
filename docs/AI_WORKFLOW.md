# EDUKASS — рабочая модель Chat, Work, Codex и GitHub

Статус: утверждённый canonical-процесс EDUKASS.
Дата утверждения владельцем: 26.08.2026.

Цель документа — выбирать подходящий режим работы, сохранять решения и не
смешивать разрешение на редактирование с разрешением на Git- или release-действия.

## Как читать нормативность

- **MUST / Canonical rule** — существующее обязательное правило или явное
  решение владельца.
- **DEFAULT / Recommended** — рекомендуемая практика по умолчанию; владелец
  может задать другой процесс для конкретной задачи.
- **EXPERIMENT / Hypothesis** — идея для проверки, а не рабочее обязательство.
- **REFERENCE** — пример качества или реализации без буквального копирования.

## 1. DEFAULT / Recommended — выбор режима

### Chat

Chat обычно подходит для обсуждения идеи и цели, педагогического анализа,
сравнения вариантов, принятия решений, формулирования требований и короткой
работы с текстом.

### Work

Work имеет смысл для действительно длинной многошаговой агентной задачи:
исследовательского пакета, координации многих источников или большого связанного
результата. Для простого обсуждения, одного документа или небольшого решения он
не обязателен.

### Codex

Codex обычно используется для фактической работы с репозиторием: кода, Git,
документации, конфигурации, автоматических и визуальных проверок, diff и
релизных кандидатов.

Выбор режима — рекомендация, а не запрет владельцу использовать другой режим.

## 2. MUST / Canonical rule — границы Codex

- До изменения Codex читает применимые `AGENTS.md` и canonical-документы.
- Codex изменяет только слой, разрешённый текущей задачей.
- Кандидат стандарта не разрешает автоматически переделывать legacy-продукт.
- Расхождение кода и стандарта проверяется; ни код, ни стандарт не
  переписываются молча.
- Codex не подменяет owner approval и не получает полномочие на публикацию по
  умолчанию.

## 3. MUST / Canonical rule — отдельные разрешения

Каждое действие имеет собственную границу полномочий:

1. **Edit** — изменение файлов в явно заданном scope задачи.
2. **Local commit** — создание commit в текущей рабочей или feature-ветке.
3. **Push feature branch** — отправка конкретной рабочей ветки в remote.
4. **Merge to main** — включение изменений в `main`.
5. **Publication / deployment** — выпуск на публичный сайт или в production.

Правила разрешений:

- Owner approval результата не означает автоматически разрешение на commit,
  push, merge или публикацию.
- Разрешение на edit не означает разрешение на local commit.
- Разрешение на commit не означает разрешение на push.
- Разрешение на push feature branch не означает разрешение на merge.
- Разрешение на merge не означает автоматически разрешение на публикацию, если
  публикация не была включена в тот же явный scope.
- Безопасный промежуточный local commit в рабочей ветке допустим только тогда,
  когда local commit явно входит в scope задачи.
- Merge в `main` и publication/deployment требуют явного разрешения владельца.
- `main`, production, GitHub Pages, DNS и `CNAME` никогда не меняются на основе
  подразумеваемого согласия.
- Владелец может выдать несколько полномочий одним явным пакетом для конкретной
  задачи, например: «commit + push feature branch, но не merge/publish».
- Агент не расширяет пакет полномочий самостоятельно.

## 4. MUST / Canonical rule — GitHub canonical memory

- Принятые правила хранятся в репозитории, а не только в чатах.
- `docs/PROJECT_PASSPORT.md` и специализированные документы в `docs/` являются
  canonical-путями текущих утверждённых правил своих областей.
- Пять маршрутизируемых документов утверждены владельцем и являются canonical в
  своих областях.
- Исторические README, release reports, versioned passports и snapshots могут
  содержать устаревшее состояние и не переопределяют canonical-документы.
- Фактическая реализация продукта определяется текущим кодом.
- Расхождение кода с canonical-стандартом требует проверки и решения, а не
  молчаливого переписывания кода или стандарта.
- Изменение утверждённого стандарта требует owner approval.
- Идея, рекомендация и эксперимент не становятся стандартом до owner approval.
- Исторические файлы не удаляются без отдельного указания владельца.

Для публичных metadata материалов source of truth — `data/catalog.json`.

## 5. DEFAULT / Recommended — жизненный цикл решения

Если владелец не задал другой процесс, рекомендуется:

1. сформулировать цель, педагогику, ограничения и критерии приёмки;
2. выбрать Chat, Work или Codex по характеру задачи;
3. передать в Codex ограниченный scope и список защищённых слоёв;
4. для изолированной реализации использовать рабочую или feature-ветку;
5. показать владельцу diff, результаты проверок и фактический пользовательский
   результат;
6. выполнить только те commit, push, merge и publication-действия, которые
   прямо включены владельцем в scope;
7. после утверждённого системного изменения обновить только затронутый source of
   truth.

Отдельная ветка является рекомендуемым способом изоляции, но не вечным запретом
на другой явно утверждённый владельцем Git-процесс. Owner approval на шаге 5 не
расширяет полномочия шага 6.

## 6. Статусы артефактов

### MUST / Canonical rule

- **Кандидат** — подготовлен к review, но ещё не является обязательным стандартом.
- **Утверждён** — прямо принят владельцем и становится canonical в своей области.
- **Эксперимент** — проверяет гипотезу и не переносится автоматически в другие
  продукты.
- **Исторический** — описывает прошлую контрольную точку и требует сверки с
  текущим кодом и canonical-документами.

Статус пишется внутри документа или однозначно следует из canonical routing.
Молчание не считается утверждением.

## 7. DEFAULT / Recommended — handoff задачи

При передаче между ChatGPT и Codex полезно явно указывать:

- цель и ожидаемый пользовательский результат;
- принятые решения и открытые вопросы;
- разрешённые и запрещённые слои;
- ссылки на canonical-документы и reference-файлы;
- критерии проверки и owner approval;
- отдельно разрешения на edit, commit, feature push, merge и publication;
- состояние реализации без создания новой версии паспорта.

Это рекомендуемый состав handoff, а не обязательная схема данных.

## 8. EXPERIMENT / Hypothesis — общий handoff-механизм

Общий task/handoff-механизм в репозитории может в будущем уменьшить ручное
копирование задач. Его формат, место хранения, жизненный цикл и связь с ChatGPT
или Codex пока не утверждены. Этот документ не требует создавать такую систему
и не запрещает владельцу экспериментировать с её вариантами.

## 9. Быстрый ориентир

- Обсуждение, педагогика или решение — обычно **Chat**.
- Длинная автономная многошаговая работа — рассмотреть **Work**.
- Код, Git, репозиторий и проверки — обычно **Codex**.
- Утверждённое правило или reference — сохранить в **GitHub canonical memory**.
- Любое изменение состояния Git или публикации — сначала сверить отдельное
  явное полномочие из текущей задачи.
