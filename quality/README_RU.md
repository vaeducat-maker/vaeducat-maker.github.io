# EDUKASS Quality Gate — приёмка результата

**Статус:** технический стандарт для новых и изменяемых продуктов EDUKASS.

## Главный принцип

«Файл существует», «кнопка нажимается», «тест зелёный» — не подтверждают, что
ребёнок увидит утверждённый результат. До реализации агент фиксирует конечные
проверяемые условия и сохраняет исходные эталоны в `quality/contracts/`.

## Обязательный цикл

1. **До программирования:** перечислить эталонные файлы, согласованные тексты,
   поведение, устройства, правила сохранения прогресса и ожидаемые переходы.
   Фиксировать конкретные *наблюдаемые* критерии приёмки.
2. **Защита исходников:** утверждённые ассеты регистрируются с контрольной
   суммой в контракте. Любое изменение файла или состава изображений вызывает
   отказ, пока владелец явно не утвердит замену эталона.
3. **Отрицательный контроль:** тестовая подмена эталона, отсутствующий файл и
   смена идентификатора должны давать красный статус проверки; иначе тест
   считается бесполезным.
4. **Реальный мобильный браузер:** робот открывает приложение, решает задания,
   выбирает награды, закрывает диалоги, нажимает стрелки/Android Back, сохраняет
   и восстанавливает прогресс. Нужны снимки реального экрана.
5. **Полное визуальное сравнение:** для изображений тестируется именно игровой
   canvas, а не генератор превью. Для 550/550 все пиксели должны
   соответствовать оригинальному изображению в режиме contain — ни одна часть
   оригинала не обрезается. Каждый из 50 миров сравнивается с эталоном.
6. **Запрет выпуска:** тестовая публикация в Cloudflare запускается только
   после успешного Quality Gate. Артефакты, скриншоты и журнал должны
   сохраняться даже при неуспешном тесте.
7. **Отчёт без преувеличения:** утверждение «проверено» допускается только с
   номером прогона, точным SHA коммита, числом тестов, красными пунктами и
   ссылкой на отчёт. Запрещено выдавать успешную проверку наличия файлов за
   визуальную приёмку. Художественную оценку делает владелец.

## Текущие команды

```bash
node scripts/quality-verify-contracts.js
node scripts/quality-test-contracts.js
node scripts/stolbiki-pedagogy-gate.js
node scripts/stolbiki-world-simulation.js
NODE_PATH=... node scripts/stolbiki-prelaunch-audit.js
```

Последняя команда выполняется в GitHub Actions с Playwright Chromium.
Тестовый ученик использует отдельный namespace в localStorage: реальные
сохранения не переписываются.

## Как добавлять новые продукты

Для нового изделия зарегистрировать отдельный JSON-контракт с именем продукта,
путями утверждённых артефактов и измеримыми условиями. Если нужен другой тип
контракта, расширить `scripts/quality-verify-contracts.js` новым валидатором;
не применять игровую математику к печатному PDF или словарным карточкам.
Для новых интерактивных продуктов добавить сценарий Playwright и скриншоты;
для PDF — сравнение страниц/размеров и вёрстки; для учебных тренажёров также
оставить независимый педагогический аудит.

**Ограничения:** любые проверки ограничены покрытыми сценариями. Изменение
самого контракта и системы проверки в одном коммите потенциально позволяет
обойти контроль; полный запрет такого обхода требует настроенных GitHub
branch protection / CODEOWNERS и обязательного независимого утверждения.
GitHub Pages, если он публикует напрямую из ветки main, может обходить
Quality Gate — это настраивается отдельно в Pages Settings.

## Автоматический учёт ВСЕХ продуктов (без надежды на память агента)

`quality/product-registry.json` — обязательный реестр игровых и учебных разделов.
Статус `verified` означает наличие **собственного** контракта эталона
и исполняемого аудита конечного результата. Статус `requires-individual-audit`
не означает «тесты пройдены»; это существующий продукт без достаточной
автоматизированной проверки пользовательского результата.

Перед публикацией `scripts/quality-check-product-coverage.js` получает список
**изменённых файлов из Git** и блокирует выпуск, если в нём есть:

- новый незарегистрированный продукт в `games/`, `materials/` или `proov/`;
- любое изменение продукта со статусом `requires-individual-audit`;
- изменение общего публичного ассета, PDF или главного экрана без явной
  привязки к продукту и его тестам;
- «пометка verified» без индивидуального контракта и реального аудита.

Сами тесты запрета, включая специально внесённые нарушения, лежат в
`scripts/quality-test-product-coverage.js`. Результат записывается в
`artifacts/edukass-quality/product-coverage.md`.

`scripts/quality-run-product-audits.js` автоматически запускает
индивидуальные тесты **всех** `verified` продуктов после установки браузера.
По мере добавления новых проверенных продуктов не требуется вручную
вспоминать, что нужно добавить их в CI — достаточно зарегистрировать
продукт с правильным контрактом и тестом.

Ключевое ограничение: реестр охватывает файлы **этого GitHub-репозитория**.
Другие репозитории, внешние приложения, Canva/PDF вне репозитория и чужие
проекты требуют подключения своих источников. В GitHub Pages, настроенном на
мгновенную публикацию из `main`, необходимо отдельно включить branch
protection/rulesets и обязательную проверку Quality Gate на Pull Request.
Сам CI не может гарантировать, что изменения попадут в `main` только через PR.
